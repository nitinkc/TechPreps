JBehave Basics & Applied Overview

Summary

BDD (Behavior-Driven Development): write executable specifications in human-readable form (Gherkin/JBehave stories) mapped to automated step code.

  • Goals: better collaboration, living documentation, clear acceptance criteria.
  • Use BDD for business-facing behaviour and complex workflows.
Use ←/→ or click the arrows to navigate slides. Press H for help.

Basics: BDD

  • Write scenarios in Given/When/Then form.
  • Map examples to step implementations to make them executable.
  • Keep stories business-focused and small.

Benefits

  • Shared understanding, living documentation, automated acceptance tests.

Test Types

  • Component: fast, isolated (mock external deps).
  • Integration: multiple components / DB interactions.
  • Functional / E2E: full user/business flows.
  • Regression: broad suites before release.
  • Smoke: quick critical-path checks.

Tip: Tag stories with @testType to filter CI runs.

Decision Guide

  • Single class/service → Component
  • Multiple services / DB → Integration
  • Full business flow → Functional/E2E
mvn test -Dmeta.filter="+testType component"

Story Anatomy (example)

Meta:
@component rtdx-product-flow

Narrative: rtdx-product-recipe-service-flow

Scenario: (1) opc create smoke
Meta: @testType functional smoke
Given initialize the test with <lineItemSku> <lineItemQty> ...
Examples:
|testcaseid |country |lineItemSku |...

Angle-bracket placeholders map to Examples columns; values are case-sensitive.

Step Definitions

@Given("publish $eventType event to EH using file $xmlfile with $countryCode")
public void publishEvent(@Named("eventType") String eventType, @Named("xmlfile") String xmlFile, @Named("countryCode") String countryCode) { /* ... */ }

Keep patterns stable; changing annotation text breaks binding.

Test Data & Utilities

  • ThreadLocal `testData` for per-scenario values.
  • `payloadGeneratorService` to build payloads from templates.
  • `convertPayloadToObject` and `databaseClientService` for validation & cleanup.

Publishing, Ingestion & Validation

  • Prefer polling vs fixed sleeps for ingestion completion.
  • Validate by querying DB, deserializing domain models, comparing JSON structures.
  • Assert counts and deep equality; include descriptive messages.

Cleanup Strategy

  • Per-scenario cleanup steps to remove inserted rows.
  • Use `@AfterStories` for global teardown (consumer groups, etc.).
  • Make cleanup idempotent.

Performance & Reliability

  • Replace Thread.sleep with polling and timeouts.
  • Consider batching inserts.
  • Introduce soft assertions for richer failure reports if needed.

Meta Tags & CI

Use @testType (component/integration/functional/smoke/regression). Optionally add @priority or @duration.

Example: BPC Ingestion (excerpt)

Scenario: Check bpc ingestion ...
Meta: @testType component regression
Given Dependency publish <dependencyEventType> and publish <eventType> with <countryCodes>
Then wait for <delay> seconds
Then validate <eventType> record

Consolidate repeated cleanup into lifecycle hooks where safe.

Common Pitfalls

  • Changing step annotation text without updating stories.
  • Mismatched example headers vs placeholders.
  • Overuse of sleeps -> slow/flaky tests.
  • Skipping cleanup -> environment contamination.

Actionable Improvements

  • Replace sleeps with polling loops and configurable timeouts.
  • Add BeforeScenario isolation/cleanup hooks.
  • Introduce soft assertions and CSV-to-Examples tools.
